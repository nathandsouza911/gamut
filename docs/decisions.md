# Decisions

## 2026-11-15: Project name is GAMUT
Chosen by the owner. Python package `gamut` lives under `backend/app`; images `gamut-web` and `gamut-worker`.

## 2026-11-15: wgasuite NOT checked (unresolved)
The owner chose to skip the prior-art check against wgasuite. This remains an open question and is unresolved.

## 2026-11-15: Deliberate change: asymmetric key wrapping (X25519)
The spec says the API encrypts uploads and that the API must not hold the master key. Both hold only if wrapping uses a public key. The "master key" is an X25519 key pair. The API receives only the public key (`GAMUT_CREDENTIAL_PUBLIC_KEY`); the worker receives the private key (`GAMUT_CREDENTIAL_PRIVATE_KEY_FILE`). Each upload is encrypted with a random AES-256-GCM data key, wrapped with ECIES (ephemeral X25519 key, HKDF-SHA256 with info `gamut-dek-wrap-v1`, then AES-256-GCM).

## 2026-11-15: Deliberate change: the API serves the built UI
No separate frontend container. Compose has exactly three services: `web`, `worker`, `db`.

## 2026-11-15: Deliberate change: a ninth table, `sessions`
Sessions are stored server-side so they can be revoked. The cookie carries only a random session id.

## 2026-11-15: GAM7 pinned to 7.52.3
`gam7==7.52.3`, the latest version on PyPI on 2026-11-15 (checked with `pip index versions gam7`). Installed from PyPI, never vendored. Its Apache-2.0 `LICENSE` is copied into the image at `/usr/share/doc/gam7/`.

## 2026-11-15: Backend tests run in Docker
The development host is Windows with Python 3.10 only; the backend needs Python 3.12 and Linux. Backend verification runs through `docker-compose.test.yml` (`testdb` postgres:16 and a `tests` service built from the Dockerfile `dev` target). CI runs natively on Ubuntu with Python 3.12 and a Postgres service.

## 2026-11-15: Source repository URL is a placeholder
`GAMUT_SOURCE_URL` defaults to `https://github.com/OWNER/gamut` until the owner supplies the real repository.

## 2026-11-15: Panel users are pre-registered; OIDC never creates users
An owner adds a user with `POST /api/users` (email, display name). OIDC sign-in only succeeds for an existing user with a verified email; the first sign-in links the provider subject to the user, and a later sign-in with a different subject for that email is refused. Unknown emails get 403 and an `auth.login_failed` audit event. Tenant admins and owners grant roles with `POST /api/tenants/{tenant_id}/members` (`{email, role}`, role admin, technician or auditor); an unknown email gets 422 telling the caller to have an owner add the user first.

## 2026-11-15: Sessions and CSRF
The session cookie (`gamut_session`, HttpOnly, Secure, SameSite=Lax) holds a random 32-byte id; only its SHA-256 is stored. Sessions end 12 h after creation or after 2 h idle. Each session has a random CSRF token, sent at login in a readable `gamut_csrf` cookie (Secure, SameSite=Lax). POST, PUT, PATCH and DELETE must send `X-CSRF-Token` equal to both the cookie and the session's stored token. The check is part of authentication, so every authenticated state change is covered; a test enumerates the routes to prove it. The login endpoints are exempt and rate-limited instead. The OIDC state and nonce travel in a separate short-lived cookie (`gamut_oidc`, signed with `GAMUT_SECRET_KEY`, path `/api/auth`, 10 minutes).

## 2026-11-15: Tenant isolation is enforced by the route class
Every route with a `{tenant_id}` path parameter uses `TenantScopedRoute`, which checks the session and the caller's membership before FastAPI reads the body. A non-member gets 404 (never 422 or 403), as if the tenant did not exist. `create_app` refuses to start if a `{tenant_id}` route uses another route class, and `tests/test_tenant_isolation.py` enumerates the app's routes so new routes are covered automatically.

## 2026-11-15: Rate limits are per web process (Milestone 1)
Login (10 per minute per client IP) and job creation (30 per minute per user) use an in-memory sliding window. The counts reset on restart and are kept separately by each web process. GAMUT runs one web process; a shared store is needed if that changes. Behind a reverse proxy the client IP comes from `X-Forwarded-For`, trusted only from `GAMUT_FORWARDED_ALLOW_IPS`.

## 2026-11-15: OIDC sign-in is optional; the bootstrap owner always works
OIDC is enabled when `GAMUT_OIDC_CLIENT_ID` and `GAMUT_OIDC_CLIENT_SECRET` are set (then `GAMUT_PUBLIC_BASE_URL` is required). Without it, `/api/auth/login` returns 503 and only the bootstrap owner can sign in. The bootstrap owner is created once from `GAMUT_BOOTSTRAP_ADMIN_EMAIL`/`GAMUT_BOOTSTRAP_ADMIN_PASSWORD` (argon2id); later starts never change it, and every use is audited as `auth.bootstrap_login`.

## 2026-11-15: Runner design (Task 4)
`run_gam` runs the binary from `GAMUT_GAM_BIN` with an argument list, `shell=False`, no inherited environment: exactly `PATH=/usr/local/bin:/usr/bin:/bin` (fixed: the images keep python3 and gam there), `HOME` and `GAMCFGDIR` set to the config directory, `LANG=C.UTF-8`, and (since Task 5 fix 1) `TMPDIR` = the config directory, so GAM's temporary files (it uses Python's `TemporaryFile` for CSV handling) stay inside the per-job directory that is removed afterwards. It starts GAM in its own session; on timeout the whole process group gets SIGKILL and the result has `timed_out=True`, exit code 124. A missing binary gives exit code 127. Output is read fully and then capped per stream (memory is bounded only by the timeout). `redact_argv` removes `subject` and `message` values and any `password` value except `random`; callers store only redacted argv. Fake gam finds its scenario and log next to the script (the runner's environment cannot carry `FAKE_GAM_*`); the env variables remain as optional overrides.

## 2026-11-15: Tenant domain matching
`assert_in_tenant` needs an exact domain match; subdomains match only for an entry written `*.acme.com` (which does not cover `acme.com`). `Email` trims spaces only, so a trailing newline is rejected.

## 2026-11-15: GAM7 configuration files and GAMCFGDIR (Task 5)
Sources: the GAM wiki pages gam.cfg (https://github.com/GAM-team/GAM/wiki/gam.cfg) and Authorization (https://github.com/GAM-team/GAM/wiki/Authorization), plus the pinned gam7 7.52.3 source (`gam/gamlib/glcfg.py`, `gam/__init__.py`).
- Files GAM keeps in its config directory: `gam.cfg`, `oauth2.txt` (the admin OAuth client: client id, client secret and refresh token; the source writes `client_secret` into it), `oauth2service.json` (the service account and its private key), `client_secrets.json` (the OAuth client, needed only to create a new `oauth2.txt` or for project commands) and the optional `extra_args.txt`. `cacerts.pem` ships inside GAM.
- `GAMCFGDIR` sets where `gam.cfg` is read. With no `gam.cfg`, GAM writes a default one into that directory with `config_dir` = the directory, plus `gamcache/` and `Downloads/` (observed with `gam version` in an empty directory).
- `GAMCFGDIR` isolates the files only while `gam.cfg` agrees: `config_dir`, `oauth2_txt`, `oauth2service_json`, `client_secrets_json`, `cache_dir`, `drive_dir`, `cacerts_pem`, `cmdlog`, `input_dir` and `extra_args` accept absolute paths (`_getCfgFile` uses an absolute value as is). A `gam.cfg` copied from the operator's machine also holds that machine's absolute `config_dir`.
- **Allow-list:** `oauth2.txt` and `oauth2service.json` (both required), `client_secrets.json` (optional). **`gam.cfg` is refused**, so GAM always writes its own default `gam.cfg` inside the per-job directory and every path stays inside it. `extra_args.txt` is not accepted (not needed). Each file at most 256 KB and must be a JSON object; anything else is rejected (422, 413 for size) without echoing contents.
- **A service account alone cannot run every offboarding step** in the Milestone 1 setup: directory actions (suspend, password reset, signout, deprovision, group removal, delete, `info domain`) and data transfers use the admin OAuth client in `oauth2.txt` (source: `buildGAPIObject(API.DIRECTORY)` / `API.DATATRANSFER`); the Gmail vacation step and `check serviceaccount` use the service account with domain-wide delegation (`buildGAPIServiceObject(API.GMAIL, user)`). GAM's delegated-admin service account (`enable_dasa` in `gam.cfg`) could remove `oauth2.txt`; it is a Milestone 2 question (spec), and it would need a `gam.cfg` setting that GAMUT then writes itself rather than accepting an upload.

## 2026-11-15: Credential upload, keys and storage (Task 5)
- `PUT /api/tenants/{tenant_id}/credentials` (owner, multipart field `files`, one part per file) seals all files as one bundle and replaces any earlier bundle; `DELETE` removes it. Both are audited with file names only (`tenant.credentials.upload|replace|delete`). Responses and `GET /api/tenants[/{id}]` show `has_credentials`, `credential_files` (names) and `credentials_uploaded_at`, never contents.
- New credentials are untested, so an upload or delete puts an active or degraded tenant back to `pending` (a disabled tenant stays disabled). An upload also queues a health-check job when the tenant has an `admin_email` (spec import flow). `PATCH /api/tenants/{tenant_id}` (owner) sets `admin_email` (must be in the tenant's domains) and the extra domains.
- `DELETE /api/tenants/{tenant_id}` (owner) deletes the tenant; credentials, memberships and jobs cascade; audit events stay (`tenant.delete`).
- Key encoding: `GAMUT_CREDENTIAL_PUBLIC_KEY` is base64 of the raw 32-byte X25519 public key; the private key file is unencrypted PKCS#8 PEM. `gamut gen-keys PRIVATE_KEY_FILE` writes it with mode 0600 (never overwriting) and prints the public key line. The web app refuses to start with a missing, example or malformed public key; `gamut worker` exits non-zero with `credential private key missing`, `credential private key is the example value` or `credential private key is not a valid X25519 key`.
- The tenant id is authenticated (AEAD associated data) in both the bundle and the wrapped key, so a bundle copied into another tenant's row does not decrypt.
- The worker decrypts into `GAMUT_JOB_DIR` (default `/run/gamut-jobs`, the worker's tmpfs): one mode-0700 directory per job run, files 0600, removed in `finally`.
- Stored step output is capped (64,000 characters) and scrubbed: any value of `client_secret`, `refresh_token`, `token`, `access_token`, `id_token`, `private_key` or `private_key_id` from the decrypted files (and each line of a multi-line value) is replaced with `[redacted]` before it is stored, in case GAM ever prints one. Service account and client ids are kept (the operator needs the client id for domain-wide delegation).

## 2026-11-15: Health check (Task 5)
A health check is a normal job (workflow `health_check`, created by `POST /api/tenants/{tenant_id}/health-check`, owner or tenant admin, rate-limited like job creation) with two read-only steps: `info domain formatjson` (admin OAuth client) and `user <admin_email> check serviceaccount` (service account). It needs the tenant's `admin_email`, which must be in its domains (422 otherwise); disabled tenants are not checked (409). Result: pass makes the tenant `active`; fail keeps `pending` as `pending` and turns `active` into `degraded`; `last_health_message` holds the failing step's title, exit code and capped (4,000 characters), scrubbed GAM output.
**Missing scopes:** GAM has no machine-readable form for `check serviceaccount` (no CSV or JSON; exit code 10 means scopes are not authorized). GAMUT therefore does not list missing scope names itself: for exit 10 it says the scopes are not authorized and shows GAM's own output, which names each scope with PASS or FAIL. This is a known limitation against the spec's "the UI shows which scopes are missing". The daily re-run is scheduled by the worker loop (Task 6).

## 2026-11-15: Tenant route parameter matching
`check_tenant_routes` and the isolation test match `{tenant_id}` with or without a converter (`\{tenant_id(:[^}]*)?\}`), so a `{tenant_id:uuid}` route cannot bypass the route-class check.

## 2026-11-15: The worker has no writable default temp directory
The worker container's root filesystem is read-only. `gam_version()` runs `gam version` in a temporary directory under `GAMUT_JOB_DIR` (never Python's default tempdir) and caches the answer once per process and GAM binary. GAM itself gets `TMPDIR` = the job's config directory. Compose also gives the worker a small `/tmp` tmpfs (uid 10001, mode 0700, 64 MB) for any library that still uses the default tempdir.

## 2026-11-15: Job queue and worker loop (Task 6)
- **One way to create a job.** `app.jobs.queue.plan_job` validates the parameters and plans the steps; `create_job` writes the job, its steps (args redacted) and a `job.created` audit event in the caller's transaction. The Task 5 event name `job.create` became `job.created`. An existing idempotency key returns the existing job (also when a concurrent insert wins, through a savepoint); a key already used by another tenant is a 409. The health-check routes use it (upload: key `health-upload:<tenant>:<uploaded_at>`; manual: a random key per request).
- **Claiming.** `claim_next` uses `FOR UPDATE SKIP LOCKED` and also takes a transaction-level advisory lock (`CLAIM_LOCK_KEY`) for the few milliseconds of the claim. Without it, two workers could each claim a different job of the same tenant before either commits, breaking "one running job per tenant". Claimable: `queued`; `waiting` with a waiting step whose `next_poll_at` has passed; `running` whose lease expired. Tenants with a running job holding a live lease are skipped. Each claim is audited as `job.claimed` (worker id, previous status, whether a lease expired).
- **Leases.** 120 s, renewed every 30 s by a heartbeat thread (its own connection) while a job runs. A job that waits or ends has no lease. Lease and poll times come from the worker's clock; workers and the database are expected to keep NTP time.
- **Claim tokens (fencing).** Every claim stores a fresh `jobs.claim_token`. The run keeps the token it was claimed with: every commit first locks the job row (`FOR UPDATE`) and checks the token, and the heartbeat renews only `WHERE claim_token = <mine>`. A worker that lost its lease (for example cut off from the database for more than 120 s while GAM kept running) therefore writes nothing once another worker has reclaimed the job: its run stops at its next write, the heartbeat stops, and the new owner's state is never overwritten or extended. A GAM call already running is not killed: killing it could leave a change half-applied, and letting it finish (within the 300 s runner timeout) is safe because the new owner re-runs that step and steps are idempotent. Its result is discarded. Scheduled actions use the same scheme (`scheduled_actions.claim_token`): an old runner's result is dropped.
- **Runnable steps.** `pending`, `running` (left behind by a dead worker; steps are safe to run twice) and `waiting`. A `failed` step runs again only after `retry_step`; `skip_step` works only on an optional failed step. Both require a failed job, are audited (`job.step.retry`, `job.step.skip`) and queue the job again. Conflicts raise `ConflictError` (`status_code = 409`).
- **Audit.** Every step transition is audited (`job.step.running`, then `job.step.<succeeded|failed|waiting|skipped>`) with the redacted argv, exit code and GAM version, plus `job.claimed`, `job.succeeded` / `job.failed` (with `reason` when the job failed before any step ran).
- **Waiting steps.** A step that returns `waiting` makes the job `waiting` and releases its lease. The next poll is `min(30 * 2**attempts, 900)` seconds away (attempts = earlier waits of that step); a workflow's `poll_after_s` can only lengthen it, never past 900 s. When it is due, the worker claims the job again and calls the workflow's `execute()` for that step again.
- **No transaction while GAM runs.** `run_steps` commits before each step and keeps objects loaded (`expire_on_commit` off during the run), so a long GAM call never leaves the connection idle in a transaction (or holding the audit lock).
- **Errors.** A disabled tenant's job fails without running GAM. A plain `ValueError` raised by a workflow (the Workflow contract: operator-readable) is shown on the step; other exceptions show only their type. Failures of `gam version`, credential decryption or the job directory fail the job with a message instead of leaving it `running`; the lease remains the backstop for crashes.
- **Engine.** The database engine hides SQL parameters in errors (`hide_parameters=True`), because the worker logs errors.

## 2026-11-15: Google API quotas and GAM rate-limit exits
Documented quotas (checked 2026-11-15):
- **Admin SDK Directory API** (https://developers.google.com/workspace/admin/directory/v1/limits): 2,400 queries per minute per user per Google Cloud project (403 `userRateLimitExceeded`; can be raised in the Cloud console); concurrent requests per operation (403 `quotaExceeded`) and per Workspace account (429 `rateLimitExceeded`, cannot be raised), with no published numbers; creating users 10 per domain per second; deleting users 5 per domain per second; deleting group members 30 per domain per second. Google's advice: exponential backoff, 2^n seconds plus up to 1 s of jitter.
- **Data Transfer API**: no separate quota page was found (the transfers reference links none); its requests count against the Admin SDK project quotas. Recorded as unresolved.

How GAM 7.52.3 behaves (read in the pinned source in the dev image): `callGAPI` itself retries `quotaExceeded`, `rateLimitExceeded`, `userRateLimitExceeded`, `sharingRateLimitExceeded` and transient server errors (`GAPI.DEFAULT_RETRY_REASONS`) up to `api_calls_tries_limit` times (default 10) with `min(2**n, 60)` seconds of backoff. When the last try still fails it exits with `HTTP_ERROR_RC` = **9** and prints `ERROR: <status>: <reason> - <message>`. There is no exit code reserved for rate limits; 9 is used for other HTTP errors too.

Decision: a step that fails with exit code 9 **and** one of those four reasons in its output does not fail. It goes to `waiting` and is retried with the waiting-step backoff (30 s doubling to 900 s), at most 6 times in a row (`MAX_QUOTA_RETRIES`, about 30 minutes); then the step fails and can be retried by hand. The count is kept in the step's data (`quota_retries`), next to whatever the workflow stored there. Commands that catch rate-limit reasons themselves (GAM's per-entity error paths) are not detected; they fail normally. Scheduled actions are not retried on quota errors in Milestone 1.

## 2026-11-15: Scheduled actions have a lease (migration 0002)
`scheduled_actions.lease_until` and `claim_token`, and `jobs.claim_token`, were added (migration `0002_leases`). A worker marks a due action `running` with a 900 s lease and commits before running its handler, so no transaction is open while GAM runs; if that worker dies, another one claims the action again after the lease. Without the column a crashed action would stay `running` forever. Handlers are registered by name (`register_action`); each runs with the tenant's GAM files in a per-action directory and returns done, refused or failed, which is stored in `result` and audited (`scheduled_action.created`, `.started`, `.done`, `.refused`, `.failed`, `.cancelled`). A disabled tenant's action is refused without running GAM. Cancelling works only while the action is `scheduled` (409 otherwise).

## 2026-11-15: Daily health check
Each worker tick queues a `health_check` job (actor `system`) for every tenant that is not disabled, has credentials and an admin email, was last checked more than 24 hours ago (or never), and has no queued, running or waiting health check. The idempotency key (`health-daily:<tenant>:<last check>:<date>`) keeps racing workers to one job.
